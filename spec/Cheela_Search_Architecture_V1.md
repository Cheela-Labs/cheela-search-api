
# Cheela Search – AI-Native Search Engine Architecture (V1)

## Vision

Cheela Search is an AI-native search engine that gradually becomes independent of external search providers by learning from every query.

Initially it uses **Tavily** and **AnySearch** as external retrieval sources. Every externally retrieved document is cleaned, enriched, indexed into **Vespa**, and connected to a **Knowledge Graph** so future searches become faster, cheaper, and higher quality.

Unlike traditional search engines, **web pages, capabilities (actions), and knowledge graph entities are ranked together**, allowing searches to return both information and executable actions.

1. Memory-first
2. Intent-first
3. Entity-first

# High-Level Architecture

Two planes meet at Vespa and nowhere else.

The **read plane** answers questions. The **write plane** — the Console Service —
puts things in the index. They share storage, not a process, and the only
direction of travel between them is through the index and the event bus.

## Read plane — the Search Service

User
→ API Gateway
→ Query Orchestrator
→ Intent Engine
→ Query Evolution Engine
→ Context Engine
→ Retriever
→ Vespa
→ Ranking Engine
→ AI Generator
→ User

The Search Service is **read-only against Vespa**. It never crawls, never
verifies a domain, and never synchronises a manifest.

## Write plane — the Console Service

```text
                    Developer
                        │
                        ▼
                 Console Service
                        │
      ┌─────────────────┼─────────────────┐
      ▼                 ▼                 ▼
Domain Verification  SEO Pipeline  Capability Registry
      │                 │                 │
      └────────────┬────┴─────────────────┘
                   ▼
      Metadata Store • Object Storage • Event Bus
                   │
                   ▼
           Embedding Worker
                   │
                   ▼
              Vespa Indexes
                   ▲
                   │
              Search Service
```

Nothing enters either pipeline for a domain whose ownership has not been
verified. That is the ordering the diagram is drawing: verification is not a
step beside crawling and manifest sync, it is the gate in front of both.

Background services continuously improve the system.

# Architecture Decisions

Permanent decisions. Each records what was chosen and what it forecloses.

## ADR-001 — Embeddings live in Vespa, generated by a worker

Embeddings are produced by an asynchronous **Embedding Worker**, stored inside
Vespa alongside the documents they describe, and searched by Vespa's HNSW index.
The metadata store never holds a vector.

**The query side is part of this decision.** Vector search compares a *query*
vector against document vectors, and the two are only comparable if they came
from the same model. Vespa keeps its embedder component configured and uses it
for queries only — the worker embeds documents, Vespa embeds queries, and both
use the same model.

That means one model pinned in two runtimes. The version is therefore a single
configuration value that both the worker and the Vespa application package read.
A version bump landing in one and not the other does not raise an error: it
returns plausible, wrong results. Pinning it once is the mitigation.

Consequences:

- A model upgrade is a full asynchronous re-index, not a deploy.
- An unchanged document costs nothing, provided change can be detected — see
  incremental crawling.

## ADR-002 — Raw artifacts are the source of truth

Raw HTML and raw `agent-discovery.json` are stored in Object Storage. **Vespa is
a rebuildable index, never a system of record.** The metadata store holds
metadata — hashes, timestamps, verification state, version history — and never
indexed content.

The test of this decision: deleting every Vespa index must lose nothing.
Re-running the embedding and indexing workers over Object Storage must restore
the system to where it was.

This is also what makes the pipeline workers separable. Each reads an artifact
that already exists rather than requiring the previous worker to hand one over.

## ADR-003 — The Console owns ingestion

Crawling, verification, manifest synchronisation and indexing belong to the
Console Service. The Search Service serves queries and holds no write path to
Vespa.

## Recorded deviations

Two names in the source change request are implemented differently. They are
recorded here rather than absorbed silently, because both are reversible and
somebody will ask.

| Specified | Implemented as | Reason |
|---|---|---|
| MongoDB | The metadata store, on PostgreSQL | The platform migrated off MongoDB and retains no driver. Every constraint the ADRs above express — metadata not content, never a vector store, Vespa rebuildable — is unaffected by which engine holds it. Naming MongoDB would additionally split the capability registry, since the Search Service reads capabilities from PostgreSQL on the request path and that path is a non-goal. |
| Pub/Sub or Cloud Tasks | Redis Streams | The existing event bus, with consumer groups, redelivery after a crash, and signed entries. Extended with the domain, crawl and manifest streams rather than replaced. |

# Domain Verification

Ownership is the root identity for every website. Nothing crawls, no capability
registers, and no future advertising feature runs for a domain whose ownership
has not been proven.

## Methods

**DNS TXT is the recommended method.** It proves control of the domain and, with
it, every subdomain — which matters here because a capability manifest published
at `docs.example.com` is not a claim about `example.com`, and only domain-level
proof settles which of those an owner may speak for.

| Method | Status |
|---|---|
| DNS TXT | MVP, recommended |
| HTML meta tag | MVP, fallback for owners without DNS access |
| HTML file | Future |
| Cloudflare API | Future |
| Vercel API | Future |

## Flow

1. User registers a domain.
2. Platform generates a verification token.
3. User publishes the token, in DNS or in the homepage's `<head>`.
4. The Verification Worker validates ownership.
5. Platform emits `DomainVerified(domain_id)`.

Verification is re-checked on a schedule, not only once. A token removed after
the fact is a domain whose ownership can no longer be asserted.

## Database

```text
domains
-------
id
owner_id
domain
verification_token
verification_method
verification_status
verified_at
```

# Step 2: Query Evolution Engine

This is a core differentiator.

Instead of issuing one search, Cheela generates multiple retrieval hypotheses.

Example:

Query:

```
PS5
```

Expands into:

- PlayStation 5 reviews
- PlayStation 5 price
- Buy PlayStation 5
- Sony PlayStation 5

Another example:

```
Australian wildfire
```

Expands into:

- 2019–2020 Australian bushfire season
- Black Summer fires
- Australia wildfire statistics

The engine uses:

- Intent
- Knowledge Graph aliases
- Popular query memory
- Entity expansion
- Synonyms
- Query rewriting

Each hypothesis is searched independently.

Results are merged using **Reciprocal Rank Fusion (RRF)** before reranking.

This dramatically improves recall while preserving precision.

---

# Step 3: Context Engine

The Context Engine decides whether a query continues a previous search.

Example:

```
Australian wildfire
How many died?
```

Becomes:

```
How many people died in the 2019–2020 Australian bushfire season?
```

Signals:

- semantic similarity
- shared entities
- pronouns
- recent session history

Session expires after inactivity.

---

# Step 4: Retrieval

Retrieval happens in stages.

## Stage A

Search Vespa first.

Collections:

- web documents
- capabilities
- knowledge graph entities
- popular query memory

If confidence is high:

Return immediately.

## Stage B

If confidence is low:

Search external providers in parallel.

- Tavily
- AnySearch

Parallel execution minimizes latency.

---

# Step 5: Hybrid Ranking

Candidates from every source are merged.

Ranking signals:

- BM25
- semantic similarity
- authority
- freshness
- entity relevance
- capability relevance
- intent compatibility

Formula:

```
FinalScore =
IntentBoost × (
    TextScore +
    SemanticScore +
    Authority +
    Freshness +
    EntityBoost +
    CapabilityBoost +
    GraphScore
)
```

Top candidates are reranked with a cross-encoder.

# Vespa Schemas

Three logical indexes: **web**, **capability**, and a future **ads** index that
is reserved and deliberately unimplemented.

Every document carries a `_meta` object. It is internal indexing metadata —
hashes, timestamps, and verdicts this platform derived — and it is kept separate
from the indexed content so that publisher data and our data are never confused
for one another.

## Web Document

```json
{
  "id": "page_x",
  "url": "...",
  "title": "...",
  "content": "...",
  "schema": {},
  "breadcrumbs": [],
  "language": "...",
  "authority": 0.0,
  "entities": [],
  "embedding": [],
  "_meta": {
    "content_hash": "...",
    "indexed_at": "..."
  }
}
```

`schema` holds JSON-LD as published. `embedding` arrives from the Embedding
Worker rather than being generated at feed time — see ADR-001.

## Capability

The original capability object from `agent-discovery.json` is preserved
**exactly**. It is not flattened into fields of our choosing, because a manifest
is a publisher's statement and reshaping it loses whatever they said that this
schema did not anticipate.

```json
{
  "id": "github.create_issue",
  "domain": "github.com",
  "version": "1.0",
  "capability": {
    "//": "original capability object, verbatim"
  },
  "embedding": [],
  "_meta": {
    "manifest_hash": "...",
    "indexed_at": "...",
    "effects": "read",
    "callable": true
  }
}
```

**There is no `intent` field**, here or anywhere in the capability index. A
request is matched to a capability by retrieval and ranking over the embedding,
which is generated from the specification's own fields — the capability's name,
its description, and its parameter names. Nothing is inferred and stored as
though the publisher had declared it.

This does not remove the "intent compatibility" signal in Step 5's ranking
formula. That signal is `IntentBoost`, the multiplier outside the sum, and it is
computed from the *query's* classified intent — an action query prefers actions.
It reads nothing on the document, which is why it survives this rule intact.

`effects` and `callable` sit in `_meta` because they are **ours, not the
manifest's**. `effects` is derived from the capability's verb and `callable`
records whether this platform would invoke it. Both are the reason a payment
capability cannot present itself as safe: a manifest can only ever lower the
privilege we grant it, never raise it. They are metadata rather than content
precisely so that the publisher's object stays untouched.

## Entity

```ts
{
  id,
  name,
  type,
  aliases,
  popularity,
  embedding
}
```

## Query Memory

```ts
{
  query,
  normalizedQuery,
  frequency,
  clickedDocs,
  successfulCapabilities
}
```

# SEO Pipeline — the AI visibility index

Console-owned. Triggered by `DomainVerified`, and by nothing else: a domain
whose ownership is unproven is never crawled.

This is **not a PageRank system**. There is no link-popularity ranking and no
attempt to order the web. The output is a knowledge index built for AI
retrieval, and the measure of it is whether a question can be answered from it.

## Discovery order

1. `sitemap.xml`
2. `Sitemap:` declarations in `robots.txt`
3. Homepage links
4. Recursive crawl

`robots.txt` is always respected.

## Pipeline

```text
Discover URLs
      │
Fetch HTML
      │
Store Raw HTML          ← source of truth (ADR-002)
      │
Extract Content
      │
Extract Metadata
      │
Extract Entities
      │
Queue Embedding Job     ← asynchronous (ADR-001)
      │
Index in Vespa
```

Raw HTML is stored **before extraction is judged**. A page that extracts badly
today is the page a better extractor should get to re-read tomorrow, without
asking its origin for it a second time.

```text
raw-html/
    example.com/
        page.html
```

## Extraction

Readability-style extraction for the body; the rest is read from the document
head and its structured data.

| Item | Required |
|---|---|
| Title | Yes |
| H1–H6 | Yes |
| Main content | Yes |
| Meta description | Yes |
| Canonical | Yes |
| OpenGraph | Yes |
| JSON-LD | Yes |
| Breadcrumbs | Yes |
| Language | Yes |

## Entity extraction

Companies, products, technologies, people and places. These become shared
metadata across retrieval rather than per-page annotations — the same entity
found on two sites is one node, and that is what makes it worth extracting.

## Incremental crawling

Tracked per document: **content hash**, **last modified**, **etag**.

Embeddings are regenerated only when content changes. This is the rule that
makes ADR-001's asynchronous worker affordable, and it depends on conditional
requests: without `If-None-Match` and `If-Modified-Since`, there is no signal
that a page did *not* change, and every re-crawl pays to re-embed text it
already had.

The user never waits for indexing.

# Demand-Driven Crawl Scheduler

Rather than crawling randomly, Cheela expands around high-demand searches.

Priority formula:

```
0.35 × Demand
+0.30 × Authority
+0.20 × Freshness
+0.15 × GraphImportance
```

Example:

Repeated searches for Australian wildfire trigger crawling of:

- government reports
- Wikipedia
- scientific papers
- trusted news archives

# Capability Registry

Console-owned. Capabilities are indexed like documents and compete with web
pages during ranking.

## The rule

Capabilities originate **only** from:

```text
/.well-known/agent-discovery.json
```

following the Agent Discovery Spec. Do not scrape HTML. Do not infer from
OpenAPI. Do not invent fields. Do not introduce an `intent` field.

The manifest is the canonical source of truth. The reason is not purity: a
second ingest path is a second reader, and the second reader is the one that is
never exercised and breaks the first time it matters. One path, used constantly,
against real files.

## Trigger

`DomainVerified`, a manual sync, or the scheduled sync.

## Pipeline

```text
Fetch Manifest
      │
Validate Against Spec
      │
Store Raw Manifest       ← source of truth (ADR-002)
      │
Expand Into Individual Capabilities
      │
Queue Embedding Jobs
      │
Index in Vespa
```

```text
manifests/
    example.com/
        manifest.json
```

## Validation

A manifest is rejected outright if it fails any of: schema version, required
fields, duplicate capability IDs, authentication validation, endpoint
validation. Only valid manifests enter the registry — a partially accepted
manifest is a registry nobody can reason about.

## Expansion

Each capability becomes its own searchable document, with the original object
preserved exactly. See the Capability schema above.

## Scheduled sync

Every 15 minutes. If the manifest hash is unchanged, nothing happens. If it has
changed, only the capabilities that differ are updated, and version history is
preserved:

```text
capabilities              capability_versions       manifests
------------              -------------------       ---------
id                        capability_id             domain_id
domain_id                 manifest_hash             raw_json
capability_id             created_at                hash
version
status
```

`status` is what allows a capability to be withdrawn when it leaves a manifest
without destroying the record that it once existed.

# Storage Stack

| Data | Technology | Role |
|------|------------|------|
| Raw HTML and manifests | Google Cloud Storage | **Source of truth** (ADR-002) |
| Metadata | PostgreSQL | Metadata only — never indexed content, never vectors |
| Search and vectors | Vespa | **Rebuildable index**, never a system of record |
| Sessions | Redis | |
| Event bus and queues | Redis Streams | |
| Analytics | BigQuery (later) | |

The ordering of the first three rows is the architecture: if Vespa is deleted,
re-running the embedding and indexing workers over Object Storage restores it.
If Object Storage is lost, the pages must be crawled again.

# Worker Architecture

Each worker is independently deployable — its own schedule, memory, retry policy
and deploy cadence.

| Worker | Trigger |
|---|---|
| Verification | Scheduled |
| Crawl | Queue |
| Entity Extraction | Queue |
| Embedding | Queue |
| Manifest Sync | Scheduled |
| Capability Validation | Queue |
| Vespa Index | Queue |

The Console Service orchestrates them. They are separable specifically because
of ADR-002: each reads an artifact that already exists in Object Storage rather
than depending on the previous worker to hand one over.

# Why This Architecture

The long-term moat is not merely storing documents. It is the continuous feedback loop:

1. A user searches.
2. Intent clarifies meaning.
3. Query Evolution explores multiple interpretations.
4. Vespa serves cached knowledge.
5. External providers fill gaps.
6. New information is indexed.
7. Entities enrich the Knowledge Graph.
8. Future searches become faster and smarter.

Over time, Tavily and AnySearch become bootstrap providers rather than primary dependencies, while Vespa, the Knowledge Graph, and Query Memory become Cheela's proprietary retrieval layer.
